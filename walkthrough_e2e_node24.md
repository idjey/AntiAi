# Walkthrough: Quest E2E Integration & Node 24 Compat Fixes

## Overview
I have completed the investigation and fixes for the two outstanding issues:
1. **Quest E2E Integration Stability:** The timeout during the `resolve` request was caused by a 500 Internal Server Error in the backend, due to a broken SQL query referencing a non-existent column (`phashBits`) instead of `perceptualHash`.
2. **NODE-24-COMPAT:** The `undici` mock issue was resolved as the codebase had already migrated away from `undici` in favor of native `https`, leaving only an outdated comment and the CI GitHub Action constrained to Node 20. 

## Changes Made

### 1. Fix `phashBits` SQL Error in `subject-phash.repository.ts`
When the frontend was previously fixed to properly send the `perceptualHashes` array, this triggered the "nearest-neighbor" scan logic in `SubjectsService.resolve`, executing `phashRepo.nearest()`.
This repository contained a `$queryRaw` SQL statement trying to read the `"phashBits"` column from the `"subjects"` table:
- **Root Cause:** The `Subject` model in `schema.prisma` uses `perceptualHash` (a string), not `phashBits` (which is present in `ProofPerceptualHash`).
- **Fix:** Rewrote the `$queryRaw` to target `"perceptualHash" IS NOT NULL` and cast the hex string correctly using `bit_count(('x' || "perceptualHash")::bit(64) # ('x' || ${hexLiteral})::bit(64))`.

### 2. Update CI for Node 24 (NODE-24-COMPAT)
Upon inspecting the codebase, `fetchPinned` in the provenance-worker had already been refactored to use standard `http` and `https` modules instead of `undici`. 
- **Fix:** Removed the lingering outdated comment referring to the `undici` mock in `provenance.e2e-spec.ts`.
- **Fix:** Updated `.github/workflows/ci.yml` to set `node-version: '24'`, ensuring the full test suite now correctly utilizes the default Node 24 environment going forward.

## Verification

- Both fixes were committed and pushed to `fix/quest-integration` for CI execution.
